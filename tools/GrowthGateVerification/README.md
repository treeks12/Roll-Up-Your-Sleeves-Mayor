# Residential growth boundary verification

From a fresh PowerShell 7 process:

```powershell
pwsh -NoProfile -File ./tools/GrowthGateVerification/Run-Checks.ps1
```

The wrapper dot-sources `scripts/Enter-Project.ps1`. Compiler temporary files, the isolated `ActualApiBoundaryCheck.dll` and `result.json` stay under the project's `.cache/growth-gate-verification`. It requires the existing net35 reference package, installed managed DLL paths in `config/local.paths.json`, and existing pure Core/Simulation libraries. `-CoreAssemblyPath`, `-SimulationAssemblyPath` and `-RoslynDirectory` select other existing inputs; defaults use the installed checkpoint's pure libraries and .NET SDK 9.0.308. It does not build the Mod project or write `artifacts/mod`.

The three checks are deliberately separate:

- An isolated net35/C# 7.3 library compilation checks the six actual boundary source files against installed game/Harmony **metadata**, with bridge facades. That output is never executed.
- The actual boundary sources then run in memory against `NativeStubs.cs` and `Facades.cs`, using the existing pure Core/Simulation libraries. Behavior assertions cover exact native roll comparisons and extremes, not-ready/nonresidential fallback, late prospective fallback, one native call, reservation failure/exception, allocation followed by exception, commit failure, nested scopes, changed epochs, legacy class commits, native demand pass-through, NoRebuild, pre-demolition reservation and late commit-only redevelopment. The fake native create method explicitly invokes the actual global-create prefix/finalizer to check hook ordering: reserved-only TLS marker, single claimed create versus nested direct creation, critical versus phase scopes, barrier before release/class removal, native exception identity, partial false/live out-ID, owner/thread/epoch and repeated finalization. Its scope counters are facades; they do not prove the real bridge's save exclusion or phase audit. The fake native randomizer and patch installer throw if invoked; no actual native/provider implementation executes.
- Mono.Cecil and PEReader read installed `Assembly-CSharp.dll` bytes without loading it for execution. The 37 metadata checks compare five literal original IL/locals/EH fingerprints (ZoneBlock, private/residential simulation, ReleaseBuilding and StartUpgrading), feed the two installed growth instruction streams to the actual transpilers using inert instruction containers and mapped stub MethodInfo/FieldInfo operands, verify insertion/RNG/predicate counts, and reject malformed boundaries. This is shape/metadata evidence, not execution of the rewritten method in CS1.

The metadata converter assigns a fresh label for each branch and attaches it to the target instruction, matching the installed provider's `HarmonyLib.MethodBodyReader.FinalizeILCodes`. This matters for the native redevelopment Bge/Bne pair: both branches target IL_072e, but the provider supplies two distinct label IDs. The earlier per-offset converter hid that difference. Regression checks accept distinct labels on one uniquely resolved target and the equivalent shared-label representation; they reject different targets, missing targets, ambiguous targets and duplicate label definitions. Production still requires the original Bge/Bne opcodes, locals, fields, threshold, draw, original-body pins and shared destination instruction.

The bridge/capacity ledger, publication, save-pair logic and effective compatibility checks are facades in this harness. `ResidentialCapacityCompatibility.ObserveMethod` is an inert facade here; the independent PE/metadata comparisons provide only the five literal original-boundary checks. These results do not certify the real capacity ledger, patchset certificate/revalidation, Harmony emission/runtime ordering, provider Mono queries or organic gameplay. The JSON report records assertion counts, scope and hashes of the production inputs. Those integration and engine proofs require their own tests and reviewed runtime runs.
